# The walking skeleton's review: accepted risk

This page is for whoever picks up the skeleton after its review, and for anyone who needs to know what was decided about what touches a person's data, money or credentials. The review protocol stops at round 3. What round 3 left open is recorded here as accepted risk: what it is, why it's accepted, what checks it now, and who signed it off. Each finding's outcome is in [the review's index](README.md), and the decisions are in [DR-87](../../decisions.md#dr-87-what-the-walking-skeletons-review-settled-in-round-3) and [DR-88](../../decisions.md#dr-88-the-guards-residual-risks-decided).

## Round 3's fixes had no reviewer

No fourth round runs, so no reviewer read round 3's fixes. Three checks stand in for one:

- **A regression test per finding.** Each fix began with a test that failed on the old code, and the code was fixed until it passed.
- **The finding's own repro, rerun.** The reviewer's repro ran before and after each fix, and both outputs were kept.
- **The full suite on the merged tree.** It ran once with both fix branches merged, where seams between them show up, and CI ran again on the pushed commit.

## The guard's residual risks, decided

Round 3 left the mod's guard with residual risks on top of DR-85's and DR-86's, and the minor findings of rounds 2 and 3 named more. Each was checked against the code first, then decided here. The guard is a guardrail, not a sandbox ([Architecture](../../architecture.md#actors)): a rule closes a risk only when it refuses no everyday command, and where a rule can't see the risk, the guard asks rather than lets the call pass. What no tool-call rule can close is scheduled for the boundary that can, or accepted with what limits it.

| The person key is a file any program the agent runs can read (the design question under the rest). | Scheduled: M1's actor slice checks whether the session's Bash sandbox can deny every command reads of the person key, the gateway key and `serve.json`, and writes to the plugin, the data root and the state directory, with the engine reached only through the mod's tools or one resolver path the sandbox excludes. DR-88 lists what the check covers and how it reports each surface. Where the sandbox holds, that's the boundary, set by the session's settings, and the pane says when person actions rest on the guard alone. The OS keychain is rejected as the key's place: the mod reaches it only through `security` or `secret-tool`, which any command the agent runs can call too. macOS asks before each read only when the item trusts no app, so every press would prompt, and libsecret gives an unlocked item to any process of the user. Cloud sessions and containers have no keychain, so the file stays the fallback where the agent runs most on its own. The better later option is a host-held signing handle: the host signs on the mod's behalf and the mod never reads the key, in the pattern of `$.session.authorize()`. A key that signs only with the person present, such as a passkey in the canvas, is the other. Both are left for a later record. | M1's actor slice |
